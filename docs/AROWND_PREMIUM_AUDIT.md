# تدقيق Arownd Premium — الواجهة الأمامية والتسجيل

تاريخ التدقيق: 2026-11-01  
المستودع: `yaso33/arownd-v-0`  
فرع العمل: `arownd-premium`  
نقطة البداية: `95b6a2612da0bf90ddaa873ae28d1fcdf3ebbb43`

## 1. حدود التدقيق ونتيجته

تم فحص شجرة المستودع، تعليمات `AGENTS.md`، `package.json`، دليل الهوية `BRAND.md`، نظام الواجهة `docs/UI_SYSTEM.md`، وصفحات المصادقة وإنشاء المتجر وتسجيل شركات التوصيل، ومكونات الشعار والمصادقة، وملفات الخدمات ومخططات Supabase الموجودة في المستودع.

مقارنة Git بين `main` و`arownd-premium` أظهرت أن الفرعين متطابقان عند نقطة البداية أعلاه؛ لا توجد تغييرات خاصة بفرع Premium حتى الآن. لم يتم تعديل `main`، ولم تُنفذ أي تغييرات على قاعدة Supabase الحية.

هذا تدقيق ساكن للملفات والمخططات الموجودة في GitHub. لم يتم تشغيل build أو lint أو tests في بيئة تنفيذ محلية، لذلك لا تُعد أي حالة نجاح مذكورة في ملفات المشروع إثباتاً لاختبار هذا الفرع خلال هذه الجلسة.

## 3. نتائج التدقيق حسب المسار

### P0 — المصادقة واختيار نوع الحساب

**الملف:** `src/routes/auth.tsx`

- الصفحة الحالية تجمع الدخول والتسجيل واستعادة كلمة المرور وتعيين كلمة مرور جديدة.
- التسجيل الحالي ينشئ المستخدم بالبريد وكلمة المرور ويضع الاسم في بيانات الملف الوصفية، بينما ينشئ Trigger قاعدة البيانات ملف المستخدم ودور customer تلقائياً.
- لا يوجد اختيار Editorial لنوع الحساب داخل صفحة التسجيل.
- يوجد رابط استعادة كلمة المرور في موضعين في واجهة الدخول.
- يوجد Google OAuth، بينما قرار المنتج المعتمد هو البريد الإلكتروني وكلمة المرور فقط.
- توجد حماية جيدة لإعادة التوجيه الداخلية ورسائل عامة تقلل كشف وجود الحسابات، ويجب الحفاظ عليها.
- يوجد تكامل Capacitor وdeep link؛ يجب الحفاظ على تدفق العودة للتطبيق عند إعادة تصميم الصفحة.

**الملف:** `src/routes/auth_.callback.tsx`

- يستعيد جلسة Supabase ويتعامل مع OAuth/code في Capacitor وروابط إعادة تعيين كلمة المرور.
- يعتمد التحويل الافتراضي على قيمة مخزنة في sessionStorage؛ يحتاج تدفق التسجيل الجديد إلى توجيه موثوق بعد تأكيد البريد، مع الاستمرار في رفض الروابط الخارجية.

### P0 — نموذج الأدوار وإنشاء المتجر

**الملفات:** `src/routes/create-store.tsx`، `src/components/sooqy/merchant-onboarding.tsx`، `src/lib/sooqy.ts`، ومهاجرات `supabase/migrations/`.

- Trigger `handle_new_user()` ينشئ دور customer تلقائياً.
- دالة `become_merchant()` تضيف merchant إلى `user_roles` ولا تستبدل customer.
- الجدول يضمن عدم تكرار الدور نفسه للمستخدم، لكنه لا يضمن أن للمستخدم دوراً عادياً واحداً فقط.
- صفحة إنشاء المتجر تستدعي `becomeMerchant()` ثم `merchantCreateStore()` في طلبين منفصلين؛ قد ينجح الأول ويفشل الثاني، فيبقى المستخدم بدور تاجر دون متجر.
- نموذج التاجر يجمع بيانات المتجر والموقع والتصنيف وساعات العمل في صفحة طويلة واحدة، ويحتاج إلى تقسيم منطقي مع حفظ التقدم والتحقق المرحلي.

**المطلوب قبل اعتماد تدفق الدور الواحد:** تصميم انتقال آمن للبيانات الحالية متعددة الأدوار، مع استثناء admin الموثوق، ثم عملية خادمية/قاعدة بيانات ذرية لإنشاء المتجر وتعيين دور التاجر. لا يجوز استخدام `user_metadata` لتقرير صلاحيات المستخدم.

### P1 — شركات التوصيل

**الملفات:** `src/routes/delivery-register.tsx`، `src/lib/delivery.ts`، ومهاجرات شركات التوصيل.

- التسجيل الحالي يتطلب جلسة دخول مسبقة.
- النموذج يجمع اسم الشركة والهاتف واسم المسؤول والبريد ورقم الترخيص.
- إنشاء الشركة يتم بإدخال مباشر إلى الجدول عبر Supabase، وحالة الموافقة الافتراضية غير معتمدة.
- مهاجرة `20261030201916_stabilize_delivery_identity_and_tracking.sql` تفصل بيانات الشركة الخاصة عن دليل الشركات المعتمدة وتقيّد صلاحيات الإدخال والتعديل.
- يجب الإبقاء على الفصل بين إنشاء حساب الشركة وبين اعتمادها تشغيلياً؛ لا ينبغي أن يؤدي التسجيل إلى تفعيل استقبال الشحنات تلقائياً.
- ينقص الرحلة الحالية تنظيم مناطق التغطية والخدمات والوثائق وحالة الطلب والمتابعة ضمن خطوات واضحة. يجب فحص سياسات التخزين قبل بناء رفع الوثائق.

## 4. ترتيب التنفيذ المقترح

1. **P0 — تثبيت عقد المصادقة:** بريد/كلمة مرور، تأكيد البريد، استعادة كلمة المرور، callback آمن، واختيار نوع الحساب بتصميم Editorial.
2. **P0 — حسم الدور الواحد بأمان:** فحص الحسابات الحالية متعددة الأدوار، إعداد انتقال بيانات قابل للمراجعة، والإبقاء على admin منفصلاً وموثوقاً.
3. **P0 — تسجيل التاجر ذرياً:** عملية خادمية واحدة تتحقق من المستخدم وتعيّن الدور وتنشئ المتجر ضمن معاملة واحدة.
4. **P1 — رحلة شركة التوصيل:** تسجيل الشركة، حفظ البيانات، الوثائق ومناطق التغطية والخدمات، مع حالة اعتماد منفصلة.
5. **P1 — توحيد نظام الواجهة:** استخدام ألوان Arownd الأصلية وشعارها ومكونات النظام، وتحسين RTL وMobile-first والحالات الفارغة والأخطاء والتحميل.
6. **P1 — التحقق:** TypeScript وESLint وVitest وUI checks وBuild، واختبارات تدفقات التسجيل والصلاحيات والروابط على الويب وCapacitor.

## 5. حدود الأمان والنشر

- لا تُطبق أي Migration على Supabase الحية ضمن هذا التدقيق.
- قبل أي تغيير في مخطط الأدوار، يجب فحص قاعدة البيانات الحية وعدّ الحسابات متعددة الأدوار ومراجعة RLS والسياسات والدوال التابعة، مع نسخة احتياطية وخطة تراجع.
- لا يُدمج أي تغيير إلى `main` إلا بطلب صريح.
- جميع التغييرات التالية يجب أن تكون على `arownd-premium` فقط.

## 6. خلاصة

الأساس البصري والهوية الأصلية موجودان بالفعل في المشروع، ولا حاجة لإعادة اختراع العلامة أو تغيير إطار العمل. أعلى المخاطر ليست جمالية فقط؛ إنها ترابط المصادقة مع الأدوار وإنشاء المتجر واعتماد شركات التوصيل. لذلك يبدأ التنفيذ بتثبيت تدفق التسجيل والأمان والذرّية، ثم تطبيق تصميم Editorial فاخر ضمن ألوان Arownd الأصلية، ثم تعميم معايير الواجهة على بقية النطاق.
